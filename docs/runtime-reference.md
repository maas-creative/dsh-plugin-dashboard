# Project Dashboard：接続・実行のリファレンス

利用者向けの導入と操作は[README](../README.md)を参照してください。以下はDSHホストへの組み込みと追加認証の仕様です。

## DSH plugin

The package entry point and `dsh-plugin-dashboard/plugin` export load the Dashboard plugin. Configure `ledgerPath` with an absolute path to the ledger and `projectIds` with the authorized project IDs. Permissions default to an empty scope. Only explicitly trusted hosts should set `projectIds: "all"`. Hosts may inject `scopeForSession(sessionId)` for a narrower per-session scope.

`dashboard_read` reads overview, projects, tasks, deadlines, submissions and artifacts. Pagination returns snapshotVersion, observedAt, items and nextCursor. Restart pagination if the snapshot changes. Reading does not change business completion or submission receipts.

## Optional Scrum integration

Install the independently released [Scrum](https://github.com/maas-creative/dsh-plugin-scrum) into the same host environment, or set `DASHBOARD_SCRUM_PACKAGE_ROOT` to its extracted package root. Then run:

```sh
DASHBOARD_DATA="$HOME/.local/share/maas-dashboard" npm run start:with-scrum
```

The resident entry connects both plugins to one DSH host and requires Scrum. Its absence is an error. The standalone entry needs no Scrum installation. A custom host may inject `createExecutionBridge(runtime)` from `dsh-plugin-scrum/execution` into `createApp({scrumClient: bridge})`. Execution finishing does not itself mark a business task complete. Dashboard verifies the artifact hash and task version; submission receipts and deadlines remain separate business records. Scrum's HardTackle entry is `hdt` or `/hdt`.

## Antigravity OAuth configuration

Bundled Google OAuth client identifiers and secrets are not distributed. Antigravity OAuth requires your own `ANTIGRAVITY_CLIENT_ID` and `ANTIGRAVITY_CLIENT_SECRET` in the process environment. Configure your approved OAuth application with the callback URI documented by the adapter (`http://localhost:51121/oauth-callback`). A missing configuration fails before authentication requests. Provider access and Google approval are not implied by this release. OpenAI and other configured providers remain available independently.

## Local evidence tools

`dashboard_graph` refreshes and queries the code-review-graph cache of an authorized project using the installed uvx package in offline mode. It never uploads source or changes business hierarchy. Code dependency is not business ownership.

`dashboard_sources` searches local text documents and registered histories, then reads the matching source for evidence. `action:files` also finds filenames, including PDF and office documents, without claiming to have read their contents. Project-scoped sessions only read their authorized folders and source records. The trusted all-project planner also searches Documents, Desktop, Downloads, the Obsidian workspace and local Codex/Pi and configured DSH session histories. Credentials, MCP authentication settings/storage and symlink escapes are rejected. Native DSH histories expose direct user messages and visible assistant text; internal reasoning, tool payloads and relayed ledger data are omitted. Results include coverage limits, file hashes and timestamps; zero matches never establish that work is unnecessary. Text reads return nextOffset for bounded continuation through files up to 2MB, and registration quotes can cite those read offsets. PDF, DOCX and XLSX reads extract local text with page/paragraph or sheet/cell references. The configured Python (DASHBOARD_DOCUMENT_PYTHON, or the Codex bundled runtime on this host) needs pypdf and openpyxl. Inputs remain unchanged; macros and formulas are not executed. Converted files are limited to 50MB and 2 million extracted characters; Excel reads at most 5,000 rows and 100 columns per sheet. Image PDFs require OCR and are not treated as empty evidence. Word annotations outside the main body remain unread. Git ignore rules do not exclude authorized business documents from discovery.

The daily agent can return `sourceRegistrations` for work found in a source, under an existing project. `projectChanges` with type `create` can register a previously unregistered outcome from a quoted source inside the authorized folder. Same-name/same-folder projects are reused, and shared source files retain separate project bindings. Type `define` can promote an imported workspace in place after its source path, hash and exact quote are re-read. The existing task IDs, folder, history and manual setting are preserved. A missing registered folder can be restored with type `repair-location`, the exact previous cwd, and re-read evidence inside an authorized replacement folder. Existing folders and projects with unfinished execution cannot be relocated through this repair; IDs, tasks, history, state and hierarchy remain intact. Registration can continue under the latest human instruction when no newer instruction is pending, across existing and newly defined projects within the authorized scope. It cannot inherit permission to start business execution. Registration requires a quote from the current human instruction, its note timestamp, the source path and read hash, and an exact source quote. The server re-reads the source before applying the batch through the existing manager records. An existing unstarted task can be revised under the current instruction by specifying taskId and its current version, with re-read source evidence. Only the title and next action change; ID, hierarchy, state and history remain intact, and the old start grant is invalidated. Active execution, stale versions and colliding task titles are rejected. Repeated registrations reuse the same item and task; registration never creates a parent task from a generated goal label, marks work complete, or records a submission receipt. Deadlines require an explicit year, month and day in the source quote; ISO, Japanese calendar/era and slash forms normalize to one date. Exact times also require a stated zone, including Japan time/JST; date-only entries do not invent a time. Registration and hierarchy changes or dispatch occur in separate turns; updated ledger planning is requested after registration. New hierarchy instructions track individual applied changes so later batches under the same instruction remain possible without replaying earlier changes. Legacy whole-instruction markers remain closed because their individual change history is unavailable.

`node scripts/verify-source-registration.mjs` uses an isolated ledger, real phone-role Arc UI and the actual fixed model to verify instruction → source tool → evidence registration → saved response and task display. A second phone instruction moves the registered task under a fixture parent and verifies both the ledger relationship and the expanded mobile tree. This does not prove real business work, discovery of the correct business grouping, or resident execution.

Manual projects retain their setting. Daily agent dispatch is accepted for a manual project with a verbatim quote from the current human start request and its note timestamp. A source registration can save `startQuote` only for that task; `taskPlans` can then define its inputs, relative output path, action and completion criteria under the same request. The saved start is tied to the task ID, project and version, and is consumed when the public Scrum execution receipt is bound. Hierarchy moves under the same quoted human request retain that task start; unrelated edits invalidate it. Other tasks, edits and unrelated old requests cannot borrow it. Registration, design and dispatch are separate model turns, with updated ledger planning between them.

Execution transitions into review queue a new parent evaluation. Native tool result text is extracted from result.content, and the planner waits for an already running resident parent before taking the next business snapshot. After inspecting the source and artifact, parent acceptance uses Scrum's public verification API before Dashboard records business completion and its captured artifact hash. Submission receipts remain separate.

`node scripts/verify-manual-work.mjs` runs the actual resident host, fixed model, phone-role browser and installed public Scrum package in isolated storage. It exercises a single human instruction through source registration, task design, real execution, independent verification and result display. This is a test of the product path, not proof that the live business ledger is organized.

Human instructions are queued durably before waiting for the native parent. The parent can persist a concrete investigation followup under the latest instruction and wake the existing planner queue after a research-only response. Identical followups are not repeated, newer instructions supersede the pending investigation, and followups never confer permission to start business execution. Native human echoes carry the original note references so the phone conversation shows each instruction once. The daily conversation mounts the official free Arc ChatThread/ChatComposer, bundled locally via `npm run build:ui`. Source, MIT license and modifications are in ui/arc/provenance.json. `npm run test:arc-ui` checks phone-role sending, saved response display, retained drafts and errors.

The all-ledger hierarchy is available from Projects → 親子関係一覧 and directly at `/#hierarchy`. Each project groups its child projects and current tasks, with project purpose, management state and individual next actions displayed together; missing values are explicit. Past tasks, projects without current work, archived records and imported workspaces remain supplementary. Search retains the matching task’s project and task ancestors. Bulk expansion opens current work, keeping history closed. Stored memberships and statuses are unchanged. Layout follows the Digital Agency dashboard guide (2026-03-31): https://www.digital.go.jp/resources/dashboard-guidebook.

The regular state response contains the latest 60 pending history candidates and keeps registered evidence. The history search requests older candidates by title and project from the server; it does not delete or truncate stored records. State responses negotiate gzip to reduce mobile transfer time.

### コマンド審査の観測

Scrumの実行前フックで既存の許可・拒否を変えずに審査結果を記録する。`auto-review.mjs` は単純な既知コマンドをルールで識別し、複合シェルを安全と断定しない。未対応のものは設定済みのループバック `/v1/chat/completions` へ渡す。審査モデルは実作業モデルと別設定で、モデル未設定・接続失敗・不正な応答でも実行権限を変更しない。直近の本人発言のみを入力し、ツール出力・中継メッセージは除外する。履歴は本文を含めず100件まで。ダッシュボード設定画面で接続を設定・確認し、スマホは結果の閲覧のみ可能。これは自動承認や安全性保証ではなく、導入評価のための観測モード。
